# 开发反思报告：0.9.1 只读执行加固

**日期**: 2026-09-11

**提交类型**: feature / security hardening

**修改文件数**: 21 个产品、测试和文档文件（不含本报告与索引）

## 1. 概述

本次更新将 Reliable SSH MCP 从“按程序名判断只读”推进到“程序名与参数形状共同匹配”的默认拒绝模型，同时统一 MCP 输出契约、修复 CLI 帮助路径和审计语义，并补充真实主机只读冒烟测试与中英文版本说明。

## 2. 修改内容

### 修改的文件

- `src/readonly-policy.js`、`src/policy.js`、`src/fleet-server.js`：实现并接入参数级只读 profile。
- `src/server.js`、`src/index.js`、`src/package-version.js`：统一结构化输出、按需帮助信息与版本来源。
- `scripts/readonly-smoke-test.js`：增加不修改远端文件的真实主机验证。
- `test/*.test.js`：覆盖拒绝语义、审计语义、CLI 和工具注册契约。
- `README*.md`、`CHANGELOG*.md`、`package*.json`：记录 0.9.1 行为、配置和发布信息。

### 主要变更

- 只读 `exec_argv` 必须匹配内置正向 profile；未知程序、未知参数、环境变量覆盖和 stdin 默认拒绝。
- `git` 只允许 `status` 与 `rev-parse`；复杂程序暂不以通用执行入口开放。
- restricted 模板不能绕过只读策略。
- 单服务器和 Fleet 工具统一声明 `outputSchema`，同时返回兼容文本与 `structuredContent`。
- 审计记录区分策略放行、工具组禁用和传输不支持。
- `--help`、`-h` 正常退出，运行时版本统一从 `package.json` 获取。

## 3. 遇到的错误

### 错误 1：PowerShell 只读行号检索被引号规则截断

**分类**: 集成 / 解析链错误

**严重程度**: 重要

**表现**: 本地 PowerShell、工具传输层和目标解释器对引号、范围与换行的解析规则不同，复合命令在到达预期程序前已经变形。

### 错误 2：仅按程序名放行无法证明命令只读

**分类**: 安全 / 架构错误

**严重程度**: 严重

**表现**: 同一程序既可能执行查询，也可能通过参数触发修改；单一 `readOnlyPrograms` 列表无法约束参数语义。

### 错误 3：审计字段把“到达处理器”与“允许执行”混为一谈

**分类**: 逻辑 / 可观测性错误

**严重程度**: 重要

**表现**: 禁用工具组或不支持传输也可能被记录为 `allowed: true`，容易误导故障定位与安全审查。

## 4. 根本原因分析

### 为什么会出现这些错误？

- 命令经过本地 shell、MCP/SSH 传输、远端 shell和最终解释器，多层解析器并不共享一套转义规则。
- “可执行文件名称”被错误地当成了“操作语义”；但真正的副作用通常由子命令、选项、路径和输入共同决定。
- 工具注册、策略判断、处理器执行与审计记录之间缺少统一、可测试的结果契约。

### 是什么导致编写时出现这些错误？

- 依赖自由格式命令和多层内联引号，未优先采用 argv、临时脚本或专用工具。
- 白名单设计停留在程序粒度，没有先建立 fail-closed 参数语法。
- 兼容文本输出先于结构化协议演进，造成描述、Schema、运行结果和审计语义分散。

## 5. 调试过程

### 调查步骤

1. 确认解析链和失败发生的层级，停止重复同形状命令。
2. 审计 Fleet 只读入口、模板入口、审计写入点及 MCP 注册路径。
3. 将复杂程序暂时排除，只为可证明安全的 argv 形状建立正向 profile。
4. 为拒绝结果、帮助输出、版本来源、结构化输出和审计语义增加回归测试。
5. 运行项目级语法、测试、差异检查和打包检查，并由独立测评复核。

### 迭代过程

- 第二阶段：从程序白名单收紧到参数 profile，并封闭模板绕过路径。
- 第三阶段：统一输出 Schema、版本和按需帮助，降低启动上下文体积。

## 6. 经验总结

### 核心洞察

1. “只读程序”不是安全属性；只有经过审查的具体参数形状才可能被声明为只读。
2. 多层 shell 中最可靠的命令是短命令、结构化 argv 和已检查脚本，而不是更复杂的转义。
3. 审计字段必须描述真实阶段：策略是否通过、处理器是否到达、传输是否支持应分别表达。

### 预防策略

- 新增只读命令必须同时提交 profile、正反测试、文档与真实主机只读验证。
- 遇到解析失败后立即改变传输形状，并先探测实际 shell 与可用程序。
- 所有 MCP 工具维持统一 Schema 与稳定拒绝元数据，避免模型从自然语言猜测下一步。

### 识别的最佳实践

- 默认拒绝，逐个开放可证明安全的最小 argv 子集。
- 使用专用高层工具替代语义复杂的通用命令。
- 兼容文本输出与结构化输出并存，给旧客户端留出迁移窗口。

## 7. 知识提炼

### 可复用模式

- `program + argv profile + policy result + audit result` 的四段式只读执行模型。
- `outputSchema + structuredContent + legacy text` 的渐进式 MCP 契约升级。
- `探测 -> 单步执行 -> 单步验证 -> 失败即停` 的跨 shell 操作流程。

### 应避免的反模式

- 把程序名白名单当作 OS 沙箱。
- 在 PowerShell、SSH 和远端 shell 之间传递长内联脚本或深层嵌套引号。
- 对解析失败重复相同形状的命令。
- 把工具已注册或请求已到达误写成策略已允许。
